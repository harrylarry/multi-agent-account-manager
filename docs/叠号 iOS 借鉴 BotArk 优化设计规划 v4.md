## 一、三向对照评估（v2 结论 + 讨论修订）

### A. BotArk 有、叠号无

**A1. Muse 原生协议客户端（Noise）——借鉴，核心。** 协议真相替代 DOM 启发式，解锁后台检测、审批、额度；讨论后范围扩大：含发送（`chat.stream`），支撑房间与指纹探针。→ Phase 0/1/4。

**A2. 额度 Server Action（`fetchSubscriptionAction`）——借鉴。** 干掉隐藏 WebView 同步；讨论后升级：额度是房间调度的输入（A17）与指挥者选择的依据之一。→ Phase 3。

**A3. 每账号代理 fail-closed——借鉴，v2 结论已修正。** iOS 17+ 公开 API `WKWebsiteDataStore.proxyConfigurations`（HTTP CONNECT 与 SOCKS5，须在建 WKWebView 前配置；叠号最低 iOS 17.0 正好能用；muse.ai 全是 https，http 明文不走代理的坑不影响），多方信源一致确认，待 Spike 在真机上验证。用户定：代理池 + 每账号选择，http/https/socks5 都支持；设了代理则协议与 WebView 都走代理、代理挂了拒绝加载等手动换（不自动切其他代理）；没设则跟系统。池子三种添加方式都要（手动、批量粘贴、订阅导入），订阅刷新手动与自动都要。→ Phase 2。

**A4. 凭据粘贴导入（Cookie/Token/JSON）——借鉴。** 多账号逐个登录是真痛点；粘贴导入是用户自己的会话转移，无自动化登录，风控风险低。上游 v0.1.6 的"一键复制 Cookie"是配套的另一半（导出）。→ Phase 2。

**A5. 批量 OTP 导入——不做。** 价值真实，但自动填码 + 加载任意收件箱页执行 JS + 跨账号共享收件箱分区，风控与安全风险高于粘贴导入；用户账号数是个位数到十位数，粘贴导入已覆盖 90% 的省力收益。风险收益比不好，不是"用户没提"。

**A6. 协作房间——借鉴编排核心，重做角色与共识（讨论后提升为核心功能）。** BotArk 房间的真相：没有角色系统，只有 @ 接力、上下文共享（每成员看自己上次发言后的消息，至多 20 条）、`[FINAL]` 纯 prompt 约定——是"各回各的加有限接力"，不是角色分派。用户要的是指挥者/执行者/审核者/上传者共同完成任务，更接近女娲造人的 commander/executor/verifier。叠号房间：借 BotArk 的壳（轮次、接力、上下文、Stop），角色分工与门禁按 §三另做。→ Phase 4。

**A7. Hermes provider——删除。** 用户定：只做 Muse 和 Hark，Hermes 不要。连带：不用建原生聊天面。

**A8. Hark 原生（REST + SSE）——借鉴，范围扩大。** 登录仍走 WebView（better-auth + Turnstile 无法纯 API），聊天与检测走原生 REST + SSE（`/api/sync/conversation` SSE + `/api/sync/poll` 轮询双轨），检测不再依赖 DOM。用户定：Hark 基础功能包括审批，检测、通知、审批都在 App 里做，与 Muse 一致（审批接口待 Spike 探查，若 Hark 无原生审批接口则走 WebView 回退并如实告知用户）。→ Phase 3。

**A9. MCP Hub——不做本体，借鉴纪律。** 工具配置属于 agent 侧（Muse 云端 VM），不在账号管理器里配；iOS 沙盒也没有共享本地文件夹可绑。借鉴每次调用人工审批的模式与 `workspaceFiles` 的路径安全纪律（realpath + O_NOFOLLOW + TOCTOU，用于备份导出等本地文件操作）。

**A10. Slack Socket Mode——不做本体。** 用户不用 Slack；等价需求（外部触发进 agent）在 iOS 上的形态是 Share Extension / Shortcuts。→ Phase 5 待验证。

**A11. Grok / Dot / Antigravity——不做。** 用户不用这三个平台，每个都是逆向维护负担；且 Dot 文档已多处过时、Antigravity 审批无原生决议，借鉴价值也低。

**A12. 桌面桥 / QR 同步——不做。** 用户明确 iOS 独立；且 BotArk 的同步是最薄弱一环（明文 HTTP、`0.0.0.0`、无限流）。换机迁移用加密备份满足，不用实时同步。

**A13. 账号分组 + 搜索——借鉴。** 账号多了分组与搜索是必需品，成本低。→ Phase 2。

**A14. 会话管理——借鉴列表与切换。** 回滚/subagents 面板不做（网页里有，低频）。→ Phase 3。

**A15. Cron / Goals / Memories / Skills 面板——低成本顺带。** 同 RPC 通道，只读，低优先级。→ Phase 3 可选。

**A16. Sand 设计语言——借鉴视觉语言，不做 3D 角色。** 冷静极简、留白、大圆角；3D 角色是噱头，不做。

**A17. 额度与模型感知的角色分派——我们的创新（两边都没有）。** 用户定：角色分派时考虑各自额度（额度高的优先分派消耗高的角色）与背后模型（指挥者自动选择看额度与模型）。BotArk 没有（房间不看额度与模型），叠号也没有。这是房间调度的核心输入，见 §三.5、§三.10。

**A18. 模型指纹检测——我们的创新（两边都没有，用户 2026-11-22 23:49 提出）。** 用 lm-detector（Ikaleio/lm-detector，MIT）的数字指纹法识别每个账号背后的模型：探针经原生发送在隔离会话里跑，Rust SDK（`cargo add lmfpd`）在本地评分，不用把数据发给第三方。LINUX DO 已有人用它测出 muse 背后是 muse-spark-1.3、hark 背后是 opus-5.5。结果是参考库内的封闭集合排序，不是身份证明；同后端模型的账号测不出区别（那时按额度排）。→ Phase 4（依赖原生发送）。

## 二、重新评估后的架构决策

### 2.1 聊天面：WebView（结论不变，理由已算过）

原生聊天要复现富组件、工具 chips、媒体、附件，且官方网页持续演进，维护负担永久；叠号是账号管理器不是聊天客户端，聊天体验完整性优先于控制权。原生只做感知层（检测/通知/审批/额度）+ 房间发送与指纹探针（见 2.5）。Phase 5 可评估原生只读消息预览。

### 2.2 Tauri vs SwiftUI 重写：保留 Tauri

SwiftUI 的优势真实（iOS API 直达），但重写成本是整个 Rust 后端 + 前端，且 Rust 后端恰是原生 Noise 客户端的最佳落点。Swift 插件只做 iOS 专属薄层。

### 2.3 原生客户端 Rust vs Swift：Rust

`snow` 现成、tokio 已在依赖里、与 Tauri 后端同一进程、BotArk TS 实现对照移植最直接；且指纹检测的 Rust SDK（`lmfpd`）正好同栈。

### 2.4 代理：每账号代理完全可行（v2 错误纠正）

- **WebView 侧**：iOS 17+ 公开 API `WKWebsiteDataStore.proxyConfigurations`，每个账号的 DataStore 单独配代理（HTTP CONNECT / SOCKS5，支持用户名密码），建 WKWebView 前配置；换代理时重建 WebView 或 DataStore（WebKit 建议，改配置可能中断当前连接）。没配代理的账号不设 `proxyConfigurations`，走系统。
- **原生客户端侧**：reqwest / tokio-tungstenite 的 per-client 代理配置，与 WebView 侧用同一份账号代理配置。
- **代理池**：统一配置代理列表（支持 http/https/socks5 地址 + 可选认证），每账号直接从池子里选一个，不用每次填；池子不够时不共享（照抄 BotArk 的 1:1 分配，不照抄它"去重键不含密码"的小瑕疵）。三种添加方式都要：手动加、批量粘贴、订阅链接导入；订阅刷新手动与自动都要。
- **fail-closed**：设了代理的账号，代理不可读或连不上时拒绝加载并报明确错误，不静默回落直连；代理挂了等手动换，**不自动切池子里其他代理**（用户定）；没设代理的账号跟系统，不用管。
- **待 Spike 验证**：在用户真机（iOS 27）上实测 `proxyConfigurations` 生效、切换、fail-closed 行为。

### 2.5 发送决策：原生发送接受（讨论结论）

原生客户端从"只读"扩大为"可写"，含 `chat.stream` 发送，支撑房间与指纹探针。安全约束见 §六（幂等键、单发、禁自动重发、发送日志）。发送只用于房间、指纹探针与用户明确触发的操作，绝不静默代发。

### 2.6 房间与图谱的关系：取理念，不取系统（讨论结论）

女娲造人的图谱借 GitHub 文件作媒介，是"agent 不能直接沟通"时的实现方式；现在 Muse 之间已有高效沟通（双 Muse 的邮件 handoff + 房间内的原生消息直传），房间按新沟通方式适配：成员间直接消息传递，角色与验证的理念保留，图谱文件系统不搬进 App。房间内的持久记录是轻量房间状态 + 图谱式结构化记录（见 §三.9），不是 `.muse-graph/`。

## 三、房间设计（本规划的核心新内容）

### 3.1 一句话

房间是一个任务工作区：几个 Muse 账号按角色分工，通过原生消息直接配合，在一个简单聊天窗口里共同完成一件任务；**用户只看结果**——角色分派与流程推动由房间自动完成，用户只在最后确认定稿（中途可介入、可停止）。

### 3.2 角色模型

| 角色 | 谁担任 | 职责 | 额度消耗 |
|---|---|---|---|
| 指挥者 | 1 个账号（手动指定，或 App 按额度、背后模型等自动选优势最大的账号；两种模式可选） | 拆解任务、规划角色分派（含兼任）、派活、汇总、失败时换人/轮转 | 中（规划 + 汇总） |
| 执行者 | 1 个或多个账号 | 按任务动手产出（写代码、写文案、查资料） | **高**（长生成、多轮） |
| 审核者 | 1 个账号 | 检查执行者的产出，通过或打回修改 | 中（读 + 评） |
| 上传者/发布者 | 1 个账号 | 把定稿整理成最终交付物（汇总、排版、导出） | 低（整理为主） |
| 讨论者 | 多个账号（头脑风暴场景） | 自由发表观点、互相补充 | 中 |

- 角色是房间内的分工，不是账号的属性：同一账号在不同房间可担任不同角色。
- **兼任规则**：允许兼任，但须在拆解任务时规划好（如账号 B 是执行者兼上传者，相关任务都由它完成）；**互斥只限执行者不能兼审核者**，指挥者可以兼审核者；是否分拆对话（同一账号的两个角色用不同会话）看多 agent 沟通的实现方式定。
- 用户是房间的拥有者与最终确认者，不担任房间内的执行角色。

### 3.3 场景模板（多场景，一个形式，可拓充）

同一套房间形式，四个内置模板（模板只定流程与默认角色，不定死内容）；**模板可拓充，不能固定死**（内置 + 可自建）：

| 场景 | 流程 | 默认角色 |
|---|---|---|
| 代码开发 | 用户给目标 → 指挥者拆解分派 → 执行者实现 → 审核者检查（不通过打回，最多 3 轮）→ 上传者汇总交付 → 用户确认 | 指挥者 ×1、执行者 ×1–2、审核者 ×1、上传者 ×1 |
| 头脑风暴 | 用户出题 → 全体讨论者轮流发言、互相补充 → 指挥者汇总 → 上传者整理 → 用户确认 | 指挥者 ×1、讨论者 ×3–5、上传者 ×1 |
| 评审 | 用户给材料 → 执行者起草 → 审核者评审修改 → 上传者出终稿 → 用户确认 | 指挥者 ×1、执行者 ×1、审核者 ×1、上传者 ×1 |
| 群发对比 | 用户出题 → 全体成员各自独立回答 → 上传者横向对比汇总 → 用户确认 | 指挥者 ×1、执行者 ×N、上传者 ×1 |

- **四个内置模板的来源**：是我按用户举例拼的提议，不是 BotArk 的。代码开发、头脑风暴是用户 2026-11-22 22:59 回答里自己举的例子；评审、群发对比是我前面 Q2 里列的选项。BotArk 的四个模板是方案评审、联合调研、代码审查、共同起草（只是预设 brief 文案）。内置模板可按用户意见换。
- **任务目标的输入**：文字描述 + 参考资料（可贴代码、链接、补充说明）。
- 所有场景共用同一套房间机制（3.4–3.11），模板只是流程预设；用户可自定模板（定角色、定流程）。

### 3.4 沟通方式：房间内直接消息传递

- **不走 GitHub 文件**：成员间通过原生消息直接沟通。App 是中继：执行者的回复经 `chat.subscribe` 收到后，由 App 按流程发给下一个成员（`chat.stream` 发送），不经过任何共享文件。
- **上下文共享**：借 BotArk 的 cursor 机制（每成员只收自己上次发言后的新消息，至多最近 20 条），避免重复投递已见内容。
- **轻量房间状态**（取图谱理念，不取图谱系统）：房间内维护一份运行简报——目标、当前阶段、已确认的决定、待办项——随房间持久化。简报由 App 从房间消息中提炼（执行者产出确认后记一条决定），不是 `.muse-graph/` 文件系统，也不在仓库里。
- **会话隔离**：每轮用独立会话 ID（`room-turn-*`），不污染各账号的主聊天；各账号的主聊天不受房间影响。

### 3.5 分派：额度与模型感知，手动与自动两种模式

- **成员选择**：两种模式都要——手动选（建房间时勾几个账号，App 只在这些账号里分角色），或自动选（只给目标，App 从所有账号里按额度、模型挑最合适的几个参加）。
- **指挥者选择**：两种模式都要——手动指定，或 App 按账号情况（额度、背后模型等）自动选优势最大的账号。
- **角色分派**：App 知道每个账号的剩余额度（Phase 3 的原生额度同步）与背后模型（§三.10 的指纹检测），分派角色时按两者排序：**额度高的优先分派消耗高的角色**（执行者），额度低的分派消耗低的角色（上传者、审核者）；模型能力强的优先分派指挥者与执行者。
- 用户可手动覆盖 App 的建议；手动指定后 App 不再自动调整该房间的分派。
- 额度耗尽保护：某成员额度不足时，App 按 §三.8 的换人顺序处理，不让任务做到一半卡住。

### 3.6 共识与门禁（不用 `[FINAL]` prompt 约定）

- **审核门**：执行者的产出须经审核者通过才能进入交付；审核者打回时写明修改意见，执行者最多重做 **3 轮**，3 轮不过转用户裁决。
- **定稿确认**：最终交付物由**用户确认**才算定稿，不是谁先说 `[FINAL]` 谁定稿；BotArk 的 prompt 约定不采用。不确认就一直挂着，用户可要求返工。
- **随时 Stop**：用户一点停止，当前轮次立即中断（AbortController + 平台侧取消），迟到的结果丢弃。

### 3.7 房间 UI：简单聊天窗口（用户定）

不华丽：一个聊天窗口，各成员按角色头像 + 名字发言，消息按时间排列；顶部显示房间目标、当前阶段、轮次进度；底部是用户输入框（发指令、补要求、点停止）。不做 3D 角色、不做复杂编排面板。

### 3.8 失败处理（硬规则，用户定）

- **混合策略**：先换人、调角色完成任务，实在完不成再问用户。
- **换人顺序**：房间外有空闲账号，优先从房间外拉；没有则房间内角色轮转、按分配规则（额度、模型）重新分派。
- **绝对禁止**：私自改目标、简化任务、交付半成品。做不到就停下来问用户，绝不悄悄降级。
- 审核 3 轮不过、换人轮转后仍无法继续、指挥者拆解失败，都属于"实在完不成"，转用户裁决。

### 3.9 记录与复用（借鉴女娲造人图谱，用户定）

- **记录保留**：用户确认定稿后，房间记录（聊天过程、简报、决定）保留下来，可随时查看、可手动删。
- **记录方式借鉴图谱**：决定记成结构化的事实（目标、决定、结论、引用来源），不只是 raw 聊天记录；房间简报即图谱式记录的载体。
- **跨房间复用**：新房间能引用以前房间的结论；手动指定与自动推荐两种方式都要（手动：建房间时勾要引用的旧房间；自动：App 找出相关旧结论，用户确认后用上）。

### 3.10 模型指纹检测（lm-detector，用户定可利用）

- **方法**：让模型凭第一反应写约 300 个 1–355 的整数（3 条取样 prompt），分布与参考库比对，排出最像的模型与置信度；探针经原生发送在隔离会话里跑，不污染主聊天；评分用 Rust SDK（`lmfpd`）在本地做，参考数据约 3.6 MB，首次下载后缓存。
- **用途**：写进账号档案，供指挥者自动选择与角色分派参考；同时可在账号设置里展示检测结果（含置信度），用户可手动修正。
- **探针模式**：自动与手动两种都要，可设置；重测手动与自动都要，自动重测周期可自定义（服务商可能悄悄换后端模型，一次检测会过期）。
- **诚实说明**：结果是参考库内的封闭集合排序，不是身份证明；同后端模型的账号测不出区别（那时按额度排）；分词器探测用不上（要读 API 的 usage 字段，聊天界面没有）。
- **附带用途**：同一方法可验第三方中转站背后到底是不是声称的模型（不在本规划的开发范围内，只作说明）。

### 3.11 房间运行规则

- **一次只跑一个房间**，为了稳定，暂时不并行；跑着时不让开第二个，不排队，提示等当前房间跑完。
- **中途介入**：用户随时可在房间里补一句话（如"补充一点要求"），指挥者收到后重新规划，接着跑。
- **轮次上限**：默认 8 轮，可调 1–24，防止无限接力；**不设额度预算，轮次上限是唯一约束**（用户定）。
- **串行轮次**：同一房间同一时间只有一个成员在发言。
- **房间数据只存本机**（房间记录 + 简报），不上传任何服务器；备份见 Phase 3 的加密备份（全量模式含房间记录）。

## 四、目标架构（修订）

分层与 v2 相同（前端 main.ts → Rust SessionManager + `muse_native` 模块 → Swift account-session 插件 → iOS 系统），修订点：

1. **原生客户端含发送**：`muse_native` 增加 `send.rs`（`chat.stream` + 幂等键 + 单发锁 + 发送日志）。
2. **房间模块**：Rust `rooms.rs`（房间状态机、轮次调度、角色分派、额度与模型感知、简报、记录与复用）+ 前端房间聊天窗口；成员初期只限 Muse 账号，Hark 成员后补。
3. **指纹模块**：Rust `fingerprint.rs`（`lmfpd` SDK 封装：探针发送、回答解析、本地评分、参考库缓存与更新、账号档案写入）。
4. **代理层**：Rust `proxy.rs`（代理池管理：手动/批量粘贴/订阅导入、订阅刷新、每账号配置、fail-closed）+ Swift 侧 `proxyConfigurations` 应用到各账号 DataStore。
5. **Hark 客户端**：Rust `hark_client.rs`（REST + SSE，检测/通知/审批，不做聊天面）。
6. **最小方法表**补充 `chat.stream`（发送）、`chat.cancel`（停止生成）。
7. **Cookie 桥、回退链**不变；代理不可读时原生客户端拒绝直连并报明确错误。

## 五、修订后的分阶段路线（Wally 定，Muse 优先、Hark 基础可用）

### Phase 0 — 技术验证 Spike（0.1.22，不发用户可见功能）

v2 的 14 项 + v3 新增 3 项，**再新增 2 项**（共 19 项）：

| # | 新增验证项 | 方法 | 通过标准 |
|---|---|---|---|
| 18 | **模型指纹检测** | `lmfpd` Rust SDK 本地评分：给测试账号发 3 条取样 prompt，解析回答并评分 | 能排出候选模型与置信度；Muse/Hark 账号各测一次 |
| 19 | **Hark 审批接口探查** | 读 BotArk `harkClient.ts` + 抓包/实测 Hark 网页的审批请求，确认有无原生审批接口 | 有接口则记下调用方式；无接口则确认 WebView 回退方案 |

**任一核心项（认证链/握手/subscribe/发送）不通过，对应路线暂停**，不硬上。先在**非主力账号**上验证。

### Phase 1 — 原生检测 + 后台本地通知（0.2.0）⭐ 核心版本

范围同 v2：`muse_native` 模块（检测用方法）+ 自适应三档 watcher（Live/Watch/Idle）+ 静音音频保活 + 本地通知（完成/审批两种）+ 回退链 + 每账号通知开关。结算判定照抄 BotArk 修复后逻辑，防抖保留叠号的两次稳定确认。

### Phase 2 — 原生审批 + 代理池 + 粘贴导入 + 分组 + 搜索（0.2.1）

- **原生审批**：`egress.approvals` 轮询 + 审批列表 UI + 一键决策（`allow_once` / `deny`；`allow_always` 只在 App 内二次确认后可用）；通知内决策只给一次性的；**绝不自动批准**；顺带 `chat.cancel`。
- **代理池**（A3）：池子管理（手动加、批量粘贴、订阅链接导入；订阅刷新手动与自动都要）+ 每账号从池子选代理 + fail-closed（代理挂了拒绝加载、等手动换，不自动切）+ Keychain 加密存储；WebView 侧经 `proxyConfigurations` 应用，原生侧经 per-client 代理应用。
- **凭据粘贴导入**（A4）、**账号分组 + 搜索**（A13）。

### Phase 3 — 原生额度 + 会话 + Hark 基础 + 加密备份（0.2.2）

- **原生额度**（A2）：`fetchSubscriptionAction` + hash 自动发现 + 60 秒轮询；失败保留上次快照标 `stale`；`QuotaSyncRunner` 降级为回退路径。额度数据同时服务房间分派（§三.5）。
- **会话管理**（A14）：`sessions.list` 原生会话列表与切换；可选顺带 Cron/Goals/Memories/Skills 只读面板（A15）。
- **Hark 基础**（A8）：Hark 原生检测、通知与审批（REST + SSE），与 Muse 同款红点、后台通知与审批列表；登录仍走 WebView。
- **加密备份**：三种模式可选——轻量（只账号列表：别名、分组、排序、设置，不含 cookie/token）、全量（账号列表 + 代理池 + 房间记录 + 模板）、自定义（自选内容）；AES-256-GCM 加密，密钥分通道传递，**带过期校验**；恢复时覆盖还是合并由用户每次选择。

### Phase 4 — 房间 + 模型指纹（0.3.0）⭐ 第二核心版本

- **房间模块**（§三）：角色模型（含指挥者账号角色、兼任与互斥规则）+ 四个内置场景模板（可拓充）+ 直接消息传递 + 轻量房间状态 + 额度与模型感知分派 + 审核门（3 轮）与定稿确认 + 失败处理（换人顺序、硬规则）+ 记录与跨房间复用 + 简单聊天窗口 + 安全约束。
- **模型指纹**（§三.10）：探针（自动/手动，可设置）+ 本地评分 + 账号档案 + 重测（手动/自动，周期可自定义）。
- 成员初期只限 Muse 账号；Hark 成员后补（Phase 5）。一次只跑一个房间。
- 验收：代码开发场景跑通一轮完整流程（需求 → 拆解分派 → 实现 → 审核 → 交付 → 用户确认定稿）；头脑风暴场景 3 个账号讨论后汇总可用；发送零重复（幂等键验证）；额度低的账号不被分派执行者；审核 3 轮不过转用户裁决；指纹探针对 Muse/Hark 账号各测一次并有结果。

### Phase 5 — 需求待验证（不排期，先确认需求）

Share Extension / Shortcuts、原生只读消息预览、Hark 成员进房间、多房间并行、房间跨设备备份。

## 六、安全设计（修订：新增发送约束与指纹隐私）

| 项 | 设计 |
|---|---|
| 发送幂等 | 每条发送带唯一幂等键（UUID），服务端/客户端双重去重，同一键只发一次 |
| 单发锁 | 同一账号同一时间只发一条；发送中再次触发直接拒绝，不排队 |
| 禁自动重发 | 发送失败（超时/断线）不自动重发，只报失败，由用户或房间调度决定是否手动重发（Hark 的"写操作只发 1 次"同款原则） |
| 发送日志 | 所有发送记一条本地可见日志（时间、账号、房间、内容摘要），用户可查 |
| 审批 | 永不自动批准；`allow_always` 需二次确认 |
| 代理 | fail-closed（设了代理拒绝直连；挂了等手动换，不自动切）；去重键含密码；持久化失败大声报错（不学 BotArk Grok 的静默降级） |
| Cookie/token | 只在内存，永不落盘、永不进日志 |
| 指纹探针 | 探针内容是无语义整数，不含隐私；评分在本地做，不上传第三方；探针在隔离会话里跑，不污染主聊天 |
| 回退 | 原生失败 → DOM 回退 → 诚实空态；绝不谎报"没有新消息" |
| 备份 | AES-256-GCM + 密钥分通道 + 过期校验；恢复方式（覆盖/合并）由用户每次选择 |
