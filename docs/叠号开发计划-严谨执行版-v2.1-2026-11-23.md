## 0. 执行摘要

**产品定位不变：**只做 iOS 独立 App，Tauri 2 + Rust + 薄 Swift 插件；WebView 保留完整聊天页面，原生层负责感知、额度、审批、代理、房间消息发送；只支持 Muse 和 Hark，不接自建服务端，不依赖桌面桥，不做 Hermes、批量 OTP、MCP Hub 等已否决功能。采用个人侧载的现有分发路线，维持既有缓存、隔离、更新与 iOS UX 优势。

**开发顺序不变：**Phase 0 技术 Spike → Phase 1 原生检测与通知 → Phase 2 审批/代理/导入/账号组织 → Phase 3 额度/会话/Hark/备份 → Phase 4 协作房间与模型指纹 → Phase 5 未排期。**每个阶段拆成可验收的垂直切片，附技术门禁、失败路径、回归测试与证据要求。开发流程改为 GitHub 承载状态和交接、同一 Agent 优先连续实现，不再依据 Agent 身份分派职责。**

**三项最高优先级的风险门禁：**

1. **iOS 后台监测**：无自建服务端时，不能承诺 App 进入挂起/被杀后仍持续实时监听远端事件。静音音频仅可试验，不当作已成立的保活保障。未明确产品可接受的延迟与能力边界，不得宣布“实时后台通知”完成。
2. **原生发送**：客户端 UUID 只支持本地去重；如果服务端没有经验证的幂等协议，就不能宣称端到端“绝不重复”。必须有持久化发送记录、未知结果状态、禁止自动重发和人工核对流程。
3. **房间编排**：用户已决定自动完成、审核、换人、定稿确认，但这些不是靠提示词就能保证的功能；必须由 App 的持久化状态机、严格路由、结果证据、超时与恢复逻辑实现。

### 2.1 不变的产品约束（开发 Agent 不得自行调整）

| 维度 | 硬约束 |
|---|---|
| 平台 | iOS 独立、最低 iOS 17；Tauri 2、Rust 核心、Swift 系统插件；现有 GitHub Actions/Intel runner 与侧载路线 |
| 服务 | Muse 与 Hark；Phase 4 房间首版仅 Muse；无自建后台服务/桌面桥 |
| 聊天 | 完整聊天继续用 WebView；原生仅做检测/通知/审批/额度/房间发送/探针 |
| 房间 | 自动编排；用户可中途介入或停止；用户最后确认定稿；一次只运行一个房间；串行调用；不排队 |
| 角色 | 指挥者、执行者、审核者、上传者、讨论者；允许兼任，但执行者不得审核自己产出；指挥者允许兼审核者 |
| 审核 | 最多 3 次打回，随后转用户裁决；不能绕过审核交付半成品 |
| 失败 | 先换人/调整分工，实在不行才问用户；不擅改目标、不简化、不中途假装完成 |
| 调度 | 成员和指挥者均支持手动/自动；额度 + 模型仅为辅助信号；手动覆盖得到尊重 |
| 运行 | 默认 8 轮，可调 1–24；不设置额度预算；不意味着允许无限时间、无限请求或无保护的循环 |
| 代理 | 手动、批量、订阅三种录入；手动/自动刷新；一账号一代理；失败停止且不自动换池中其他代理 |
| 备份 | 轻量、全量、自定义；恢复时用户选择覆盖/合并；加密、可恢复、可验证 |
| 记录 | 定稿后保留、可删；跨房间手选或经用户确认的自动推荐 |
| 指纹 | 本地评分、隔离会话、手动/自动检测与重测；结果是概率性参考，不是认证 |

### 2.2 必须先写清楚的冲突与解释

| 编号 | 原设计中可能冲突的地方 | 本计划采用的执行解释 |
|---|---|---|
| D-01 | “手动选成员只在这些账号里分角色”与“失败优先从房间外拉账号” | **【待产品确认】**手选成员池视为硬边界；自动选成员池可以自动扩展。手选池想拉外部账号，先征得用户同意。 |
| D-02 | “手动固定角色不再自动调整”与“失败自动换人” | **【待产品确认】**手动固定的账号/角色变更先询问；仅自动分配的角色允许在规则内自动换人。 |
| D-03 | 默认 8 轮与最多 3 次审核打回，可能互相抢占次数 | **【待产品确认】**一轮定义为一次 Agent 请求—完成—入账（流式分块不另计）；先达到 8 轮或 3 次打回中的任一上限，就转用户裁决，绝不私自加轮。 |
| D-04 | “房间数据只在本机”与“多个 Muse 账号互传上下文” | 本机仅指**房间编排状态和记录的保存位置**；为让云端 Agent 工作，消息和被选择的参考材料仍会发送到 Muse 平台。必须在 UI 清楚显示传送对象与数据范围。 |
| D-05 | “全量备份”与“Cookie/token 不进备份” | 全量指本 App **可导出的业务数据**，不代表操作系统 WebKit 会话凭据也导出。不可恢复的会话须提示重新登录。 |
| D-06 | “Hark 审批与 Muse 一致”与“没有已确认的原生审批接口” | UI 体验尽量一致；技术实现先定位 **WebView 内人工审批**，不能许诺锁屏通知上一键审批。仅在 E3 验证后承诺。 |
| D-07 | “上传者交付代码/文件”与“不接服务器、不引入共享文件系统” | 先区分“文本/链接交付”和“可验证的文件/PR/commit 交付”；无可靠工具链时**不得把聊天文本包装成已写入仓库的产物**。 |
| D-08 | “停止立即中断”与远端请求无法保证撤回 | 本机立即停止后续分派并丢弃旧轮结果；远端取消是 best-effort，已发生的远端副作用不能声称撤销。 |
| D-09 | “Hark 也要自动模型指纹”与“本阶段 Hark 只开发原生检测” | **【待验证】**Hark 若无已验证的隔离会话发送能力，不能对其自动发探针。可先完成 Muse 指纹；Hark 自动探针必须另做发送 Spike，或明确让用户手动粘贴结果，不能冒充自动模式。 |

以上属于对原需求的**精确定义建议**，不是默默改变用户决定。没有最终确认时，以更保守、不越权、不泄漏的行为为默认值。

## 3. 技术架构与先决条件

### 3.1 分层职责

- **WebView 层**：维持 Muse/Hark 网页会话、账号隔离和完整聊天能力；Hark 无原生审批时允许跳转其网页流程。
- **Swift iOS 层**：各账号 `WKWebsiteDataStore`、Cookie 桥、代理配置与切换、App 生命周期、通知授权与回调、文件保护、Keychain。
- **Rust 账号服务层**：`muse-native` 的认证/Noise/订阅/发送/取消/审批/额度；Hark REST+SSE；各账号独立代理 HTTP/WS 客户端。
- **Rust 房间层**：持久化状态机、消息路由、角色分派、审核门、止损、记录索引、引用追踪、发送台账。业务流程不可只写在前端 prompt 中。
- **前端**：账号管理、状态可视化、房间单窗口、通知、恢复/裁决入口。前端可重载，但不能成为房间状态唯一持有者。

### 3.2 关键接口应先定义成结构化契约

`AccountCapability`：登录有效、原生检测、原生发送、审批能力、额度可用性、代理状态、模型识别状态，各字段带 `supported/unsupported/unknown` 和 `lastVerifiedAt`。

`SendAttempt`：`sendId, roomId, runId, stepId, accountId, conversationId, requestDigest, startedAt, status, serverReceipt?, errorCode?`。`status` 至少有 `PREPARED / IN_FLIGHT / CONFIRMED / DEFINITIVELY_FAILED / UNKNOWN`。入账与本地去重必须持久化。

`RoomRun`：`roomId, runId, goalRevision, phase, plannedRoles, roundsUsed, activeStepId, pendingUserDecision, lastCommittedEvent`。每次用户补充目标必须递增 `goalRevision`，旧响应不再推进新目标。

`HandoffEnvelope`：`sourceAccount, targetAccount, goalRevision, sourceStepId, approvedSummary, evidenceRefs, requestedAction`；跨账号内容由 App 明确组装，不能无限拼接历史聊天。

`DeliveryManifest`：`artifactType, artifactRef, producer, verifier, reviewRounds, acceptanceChecks, userApproval`。文本产物可由摘要与内容哈希定位；真实代码/文件需明确路径、可访问链接或提交哈希和验证记录。

### 3.3 协议层真实安全边界

- Noise 握手、RPC 方法名、Server Action hash、Hark REST/SSE 都是变化风险：禁止散落在 UI 里，要求统一接口、协议版本探测、超时、可观测错误及受控回退。PR #15 描述采用**手写 Noise 移植而非原设计提议的 `snow`**；不能仅因 22 项测试通过便视为协议安全审计完成，应增加负向向量、畸形帧、重放/边界测试，并评估是否需要独立实现复核，不擅自重写已验证代码。
- **发送端到端恰好一次不可预设**。若服务端不支持请求级幂等，采取“本地至多主动发一次 + 发后确认 + 结果未知时人工核对”，不自动重发，也不把 `UNKNOWN` 记作 `FAILED`。
- `chat.cancel` 和本地 Abort 只代表取消请求已发出/本地调度终止；后端是否真的停止必须按观测确认。
- 不使用 Agent 回复中的自然语言标签（例如 `[FINAL]`）直接改变状态；状态转换由 App 验证后的结构化事件触发。模型输出属于不可信内容，不能修改系统约束。
- Swift/Rust 过桥凭据在使用后清理；**注意 WebKit 的持久化 Cookie 本就由其 DataStore 管理**，禁止将“App 不主动写第二份 Cookie”写成“磁盘里绝无 Cookie”。

### 3.4 明确后台能力上限

- 前台活跃：优先订阅与事件流，检测、红点、通知可验证。
- 短暂后台执行：系统允许期间尽力工作，记录实际存活时长；不保证稳定。
- 挂起、用户强退或系统杀进程：无额外远端推送服务时，不能承诺持续收取新事件。回前台补扫并提示最后成功同步时间。
- 静音音频保活：列为受控实验，测耗电、录音/播放会话冲突、锁屏、低电量、系统杀进程和系统规则；无有效证据不得做默认可靠性承诺。若将来上架 App Store，还需评估背景模式使用目的与审核规则。
- 本地通知只在 App 已检测到新事件并创建通知请求时触发；并非服务端通知替代品。

### 3.5 代理协议要求

- `http://` → HTTP CONNECT；`https://` → 经 TLS 的 HTTP CONNECT（需实测支持）；`socks5://` → SOCKS5；认证密码放 Keychain，配置里只保存引用。
- WebView 侧每账号专属 `WKWebsiteDataStore.proxyConfigurations`；明确设置 `allowFailover = false`；Rust 的 HTTP 与 WebSocket 客户端对应设置无直连回退。
- 支持配置前检查、失败即阻断、切换后重建受影响 WebView/连接；取消代理须明确用户操作，不能由故障逻辑清掉设置。
- 验证范围：目标请求、登录、页面重定向、WS、DNS/IPv6、认证失败、代理断连、切后台恢复、切账号。通过客户端日志与**代理服务端出口日志/受控网络观测**双重证据确认“没有直连”。
- 订阅导入：明确接受的 URI/文本格式和失败提示；严格输入长度、数量与 URL 校验；订阅刷新保持旧配置原子可用，不能用坏的新内容清空代理池。

### 4.1 必须满足的合入/发布门禁

| 门禁 | 进入条件 | 退出证据 | 未通过处理 |

| G3 功能垂直切片 | 单元、集成、回归、失败路径 CI 通过 | PR 描述、测试报告、真机截图或日志 | 合入前修复或回退该切片 |

**测试要求（适用于每个 PR）**：`cargo fmt --check`、`cargo test`（受影响 crate）、`cargo clippy`（受影响 crate）、前端类型检查/构建、已有 actionlint 与 iOS 编译/IPA 构建，以及本次改动对应的自动化失败测试。某命令在当前仓库未配置时，先建立实际可运行的等价命令，不准伪报通过。使用严格静态检查的前提是先消除存量噪声或按受影响范围执行。

**关键模块测试覆盖目标**：不是笼统追求行覆盖率；对发送、审批、代理 fail-closed、房间状态转换、恢复/合并，要求**每一种合法状态转移至少有正向测试，每一个高风险失败分支至少有反例测试**。必要时加属性测试、断电/杀进程恢复测试、仿真事件与协议兼容性用例。

### 4.2 一次只做一个任务，不等于每个改动都需要重流程

- **T0 文档/注释**：当前执行 Agent 可直接修改，跑关联最小检查；无行为变化不强制真机验包。若改动很小，可在 PR/commit 留痕，不强制另开 Issue。
- **T1 小修复（局部且可回滚）**：当前执行 Agent 直接补代码和回归测试，关联已有 Issue 或在 PR 记清原因；无需因“不是自己原来的任务”转交其他 Agent。
- **T2 功能/行为变更**：GitHub Issue → 分支/PR → 当前执行 Agent 自检 + CI/测试 → 用户按风险验包 → 依权限合入；不同 Agent 审查为可选增强，不设固定人员门槛。
- **T3 高风险变更（登录、协议发送、审批、代理、恢复、房间调度）**：先 Spike/ADR，必须有失败注入、真机证据与回滚方案，用户批准后才合入。必要时增加独立复核，但**独立复核是质量措施，不是给其他 Agent 划定的专属任务**。
- **项目级偏好**：条件允许时，尽量由同一个 Agent 连续完成一个阶段乃至整个项目，包括设计核查、编码、测试、PR 与修复；只有受权限、可用性、上下文限制、阻塞或用户明确指令影响时才切换。持续开发不需要反复交接或指定新“角色”。
- 仍遵守**同一时刻只有一个主开发任务**；允许不修改主线的独立文档调查/真机验证并行，不合并互相覆盖的实现分支。

### 4.3 版本与功能开关

- 0.1.22 维持为 Spike 代码版本，**是否制作用户可见 Release 仍由用户决定**；绝不将“版本号已改”当作“已发布”。
- 0.2.0、0.2.1、0.2.2、0.3.0 保留原规划作为**拟议里程碑**，待最终确认；一个版本可有多个内部切片，但只在全量验收后正式发布。
- 高风险功能用默认关闭的功能开关（构建或配置层），未通过门禁不会意外进入日常版；使用后可独立关闭回退到旧路径。
- 发布包要附 `build SHA / 测试设备与 iOS 版本 / 变更清单 / 已知限制 / 失败回退指引`。

### Phase 1 — 0.2.0 原生感知与可兑现的通知

**依赖**：B1、C1/C2 已验证；基础事件契约和回退链已有测试。

1. **P1-1 统一事件流水线**：Muse 原生订阅 → 标准化事件 → 两次稳定确认 + 5 秒采样去重 → 账号状态；记录最后成功同步时间。保护既有红点与 WebView 逻辑。
2. **P1-2 三档 watcher**：Live/Watch/Idle 的进入、退出、退避、租约续期、低电量/无网络处理须由实际 iOS 状态驱动，不得假设挂起后定时器持续运行。
3. **P1-3 通知**：任务完成/审批待处理两类；系统通知权限拒绝时不崩溃，通知内容注意隐私，通知去重以 `accountId + eventId/稳定指纹` 为键；前台仍保留仅红点的 UX。
4. **P1-4 回退与诊断**：原生失败 → 允许的 DOM 回退 → “暂不可判定”；显示最近成功时间和失败原因，不把没检测到事件伪装成“没有事件”。
5. **P1-5 后台实验**：静音音频实验隔离在可关闭的实现中，必须提供续航/系统行为报告；不作为通知准实时的唯一成立条件。

**验收**：前台完成事件不重不漏（覆盖约定事件样本）；真实待审批项在可检测状态下提醒；切换账号/代理断网/杀进程/重启不串号；锁屏后的行为与已写明的能力边界一致；连续回归旧缓存、进程回收、导航、登录、红点。**不能持续监测时必须明确显示能力受限，而不是算成通过。**

### Phase 2 — 0.2.1 审批、代理池、凭据导入、账号组织

**依赖**：B2，C3+W 对代理支持的协议达标；P1 事件模型稳定。

1. **P2-1 原生审批**：Muse 审批列表与详情、`allow_once / deny`；`allow_always` 仅 App 内二次确认；通知快捷操作只允许不扩大授权的一次性动作；不自动批准。审批 ID、账号、会话、过期时间、最新状态必须在提交前复核。写操作未知结果时人工核对，禁止自动重发。
2. **P2-2 代理数据模型与池**：每账号 1:1 代理引用；支持手输、批量粘贴、订阅 URL 导入、手动与自动刷新；校验/去重/拒绝损坏输入/订阅失败保持旧数据；凭据 Keychain、列表脱敏。**不得自动切换其他代理或取消代理设置。**
3. **P2-3 双链路生效**：Swift WebView DataStore 代理 + Rust HTTP/WSS 代理；代理切换时销毁旧连接并安全重建；失败不可直连，界面给出可操作错误。
4. **P2-4 会话粘贴导入**：Cookie/Token/JSON 严格解析与预览；一账号只导入自身会话；清理剪贴板建议而非私自清除；失败不污染原账号；不记录敏感值。跨 App 复制本质上暴露凭据，UI 需提示风险。
5. **P2-5 分组/搜索/权限加固**：保留别名、拖拽与排序；补 storage Unix 权限和 iOS 文件保护检查；存量账号/数据无损迁移。上游 v0.1.6 **仅择取数据模型/解析思路**，不整体合并平台代码。

**验收**：审批旧项/重复点击/过期项/不同账号不能交叉决策；代理断线、密码错误、IPv6、网络切换都不直连；三种导入方式可回滚；旧账号登录状态、缓存档位、持久数据不受影响。**若代理 fail-closed 无法证明，整个代理功能不发布，其他独立切片可保留。**

### Phase 3 — 0.2.2 额度、会话、Hark、加密备份

**依赖**：B3、C4；P2 的数据迁移、Keychain 与双链路策略稳定。

1. **P3-1 额度**：原生 Server Action 主路径、自动发现 hash、失败 `stale` 快照、DOM 回退；额度字段必须携带服务商、窗口、重置时间、同步时间，不能仅存“剩余数字”。60 秒轮询是**前台可执行时的建议策略**，不是挂起后的实时承诺。
2. **P3-2 会话**：`sessions.list` 查看/切换，映射账号与原生 `conversationId`；断线时不丢映射。Cron/Goals/Memories/Skills 只读功能可选且不阻塞发布。
3. **P3-3 Hark 检测/通知/审批**：REST + SSE/poll 双轨去重；保持与 Muse 一致的状态展示与已观测的通知能力。**审批先采用 WebView 中用户手动决策**；必须提供实际页面跳转/过期审批/会话失效的验收，不要把它说成已实现原生审批或后台快捷审批。
4. **P3-4 加密备份**：保留轻量/全量/自定义，AES-256-GCM 与版本化格式；加密密钥由用户口令经适当 KDF + 随机 salt 导出（或同等可验证机制），每备份独立随机 nonce，验证完整性与格式版本。恢复前预览与冲突列表，选择覆盖/合并；恢复失败原子回滚；针对不同版本做迁移测试。
5. **P3-5 凭据与过期语义**：全量备份含账号设置、代理池非敏感字段、模板与已有房间记录（Phase 4 引入后自然支持），**不隐含导出 WebKit 登录会话或明文口令**。明确“密钥分通道”和“过期校验”各自要解决的威胁：若是临时分享备份，按用户设置校验过期；若是长期离线备份，不应默认无提示自毁。【待产品确认：到期规则与密钥通道 UX】

**验收**：服务商 hash 失效、额度跨重置窗口、Hark SSE 断流、空会话、备份错误口令/密文损坏/版本升级/合并冲突均有确定行为；同一份数据先导出后恢复，字段逐项对照一致；恢复失败不丢原始数据。

### Phase 4 — 0.3.0 房间与模型指纹（拆成五个不可跳过的子里程碑）

**依赖**：原生发送 B4 达到可接受的安全级别、P3 额度可用或 `unknown/stale` 可处理、存储恢复路径可用。**模型指纹不是手动房间能否运行的硬前置依赖。**首版仅 Muse 成员。

#### P4-A：本地持久化房间状态机（先不接模型）

- 用测试用的虚拟 Agent 构造 `CREATED → VALIDATING → PLANNING → DISPATCHING → WAITING_REPLY → REVIEWING → ASSEMBLING → PENDING_CONFIRMATION → FINALIZED`。
- 每个状态转移先持久化再执行外部副作用；处理 `PAUSED / STOPPED / NEEDS_USER / NEEDS_RECONCILIATION / FAILED`；App 重启后能够恢复到**可解释**的状态，不能因重启重复发送。
- 验证一个活跃房间互斥、没有排队，用户可看进度与轮次 1–24，默认 8，超限转用户裁决。
- 自定义模板 schema、内置四模板及版本号；非法角色/流程/人数要求被启动前拦截。

**DoD**：状态迁移表每条边有测试；强制杀进程、重开、重复系统事件不产生二次分派。

#### P4-B：单账号最小闭环 + 明确交付物

- 完成创建房间→指挥者（可手动）→一次发送→收到可核验回复→结果待确认→用户确认/返工。
- 交付类型至少区分文字、链接、文件、代码变更。**没有可访问仓库/文件的写入与核验凭据时，只允许声明文字方案或待交付，不能写“代码已提交”。**
- 发送失败变 `UNKNOWN` 时停止本轮派活，用户可选择核对会话或弃用；未核对不得重放。

**DoD**：端到端真机实测；远端结果出现但客户端丢 ACK 不能造成重复发送；交付含来源、时间、账号、可验证引用。

#### P4-C：多账号顺序接力 + 审核门 + 用户介入

- 成员通过 App 显式路由；每次仅一个成员发言，使用 `runId / stepId / accountId / conversationId / goalRevision` 双重以上隔离，迟到的旧轮回复不能进入新轮。
- 游标共享最近 20 条新消息是**容量上限**，不是唯一上下文；跨轮必要事实进入结构化简报。简报包含目标、决定、依赖、待办与来源；消息文本视为不可信输入，不能修改硬规则。
- 严格禁止执行者审核自己的产出；指挥者可兼审核者；角色兼任在运行前写入计划。审核通过是明确事件，不依赖 `[FINAL]` 字样。
- 最多 3 次审核打回；任一上限先触发就进入 `NEEDS_USER`。用户补充要求时递增 `goalRevision`，重新规划但不私自扩大目标；Stop 立即冻结本地调度并尽力取消远端请求。

**DoD**：至少 3 个账号的头脑风暴和至少 2 个执行/审核分离的代码评审流程通过；乱序、断流、超时、旧回复和用户中途改目标均能正确恢复或暂停。

#### P4-D：自动选择、失败换人、模板与记录复用

- 自动选成员/指挥者、手动固定、按额度/模型调度都使用**可解释的确定性规则**。`unknown/stale` 不得被当作“额度足够”；不同额度窗口/不同服务商的原始数字不得直接比较。指纹评分仅作为低置信度辅助，能力优先由真实可执行测试与可靠性信号提供。
- 优先已授权范围内的空闲账号；自动模式可从房间外添加账号；手动固定范围按 D-01/D-02 的保守规则先征得用户许可。代理失败、认证失效、额度不足均应停在明确状态，不暗改用户目标。
- 审核打回/换人失败/能力不足，先明确重试**是否会引发重复副作用**，再转用户裁决；绝对不允许“简化任务就算完成”。
- 记录保存原始聊天、简报、决定、证据链，可查看可删；跨房间自动推荐须由用户确认后注入，防止误引用或跨任务泄漏。

**DoD**：用模拟额度与模型档案验证稳定分派；手动固定不会被偷偷重派；某账号失联能按规则换人或停下；跨房间引用可追溯且能撤销。

#### P4-E：模型指纹产品化与 0.3.0 集成验收

- 使用经过 iOS 编译/测试的 `lmfpd` Rust SDK；三个合法探针回答才展示校准置信度，样本不完整显示“只有候选排名/不可判定”。参考库版本、校验值、更新时间随结果存档。
- 用户可手动启动探针，自动探针与自定义重测周期为可关闭的显式设置；消耗账号额度且会创建远端隔离会话，UI 必须说明。探针本地评分，不向第三方评分站点发送结果。**Muse/Hark 各需真实有效的试验结果才能标记已验收；Hark 自动探针先完成发送链路 Spike（D-09），否则明确保留未实现状态。**
- 指纹不等同模型身份，不允许自动覆盖用户手动指定的模型；识别库缺失/损坏/未知模型时房间仍能走手动或无模型信号的保守分派。
- 集成验收覆盖：代码开发（真实可验证产出→审核→汇总→用户确认）；3 账号头脑风暴；手选/自动选；3 次打回；额度不足；中途介入；网络断线；进程死亡恢复；模型未识别；记录复用。

**0.3.0 DoD**：不是“能展示一个房间聊天窗口”，而是**可追溯、能停下、能恢复、能准确说明产物真假的完整闭环**。若指纹或高级调度延期，必须明确降级影响并经用户同意，不能静默将原目标缩小后称完成。

### Phase 5 — 需求待验证（维持不排期）

Share Extension / Shortcuts、原生只读消息预览、Hark 进房间、多房间并行、跨设备房间备份。每项先写独立 ADR 和可行性 Spike，再决定版本；**不提前写死“一项 1–2 个任务单”**。

## 7. 风险登记簿与 Go/No-Go

| 风险 | 级别 | 触发信号 | 必须采取的措施 |
|---|---|---|---|
| R1 iOS 后台持续监测不成立 | **阻断 Phase 1 的“实时”承诺** | 挂起后 WSS 停止、静音音频无效或不可接受 | 调整承诺为“前台/系统允许时检测 + 回前台补扫”；用户决定是否仍发布 |

| R5 Hark 审批能力与预期不符 | 中 | WebView 无法到达审批或状态不同步 | 降为手动网页审批并清楚标记；不允许伪原生快捷审批 |
| R6 备份或迁移破坏账号数据 | 高 | 导入覆盖、解密错误、Keychain 引用失效 | 预览、事务/备份、迁移前快照、自动回滚 |
| R7 指纹误判影响调度 | 中 | 候选库缺少实际模型、置信度过高误导 | 手动覆盖优先，低置信度只作弱信号；自动探针可关闭 |
| R8 房间输出无法证明真实执行 | 高 | “已上传”无路径/提交或工具证据 | 交付 manifest 校验；无法证明则不得定稿为真实文件 |
| R9 AI Agent 自动改需求或掩盖失败 | 高 | 修改已拒绝功能、跳过测试、虚报成功 | 需求基线/门禁锁定，变更需 ADR 与用户明确批准 |
| R10 许可证、平台条款及分发风险 | 中 | 移植代码缺声明、非官方调用违反服务限制 | 保留 MIT NOTICE，检查上游许可与服务条款，必要时停用协议功能 |
| R11 Hark 指纹缺少已验证发送能力 | 中 | Hark 只能读 SSE/poll，无法在隔离会话发探针 | 独立发送 Spike；未通过则手动候选功能与 Muse 自动探针分别验收，不能宣称 Hark 自动检测 |

**风险评级规则**：任何涉及账号泄漏、审批误操作、代理直连、远端重复写入、数据不可逆丢失的问题为 **P0/阻断**；不能以 UI 完成或文档说明代替修复。

## 8. GitHub 作为项目记忆：单 Agent 优先、任意 Agent 可接续

### 8.1 核心原则：不设开发 Agent 固定角色

- **用户**决定产品范围、不可接受的风险和需要人工验包/合入的事项；这不是一个必须绑定到某个开发 Agent 的“管理员岗位”。
- **当前执行 Agent**对手头任务的完整闭环负责：理解既有需求 → 核实仓库状态 → 实现/修复 → 自检及测试 → 更新 Issue/PR → 准备验收 → 在权限允许且获批准后收尾。**它可以继续处理其他 Agent 建立的 Issue、PR 或代码，不得以“这不是我的任务/我只负责审核或规划”为由拒绝正常开发。**
- **优先保持一个 Agent 持续推进整个项目**，以减少上下文损失和协调开销；这里的“一人到底”是偏好而非写死身份。更换模型/平台/会话时不重建任务，只更换当下执行主体。
- **不固定开发分工**：不预置指挥者、程序员、审核者、整合者等身份，也不绑定模型名称、邮箱或代理平台。代码质量通过测试、CI、PR 自检与按风险进行的额外复核保障；T3 仍遵守第 4 节的独立安全门禁。
- **产品内协作房间的指挥者/执行者/审核者等角色属于 App 功能需求**，与此开发工作流完全不同；前者严格保留，不因本条改动而删减。

### 8.2 唯一可核对的上下文在哪里

| 信息 | 主记录位置 | 规则 |
|---|---|---|
| 产品需求、已确认的约束与设计调整 | 仓库版本化设计文档 / ADR，链接到相关 Issue | 用户新决定优先于旧文档；改决策留变更记录，不能只写在聊天里 |
| 任务目标、范围、依赖、状态、阻塞与下一动作 | **同一个 GitHub Issue** | 一张 Issue 对应一个可交付任务；阶段内多个验收项用 checklist，不因 Agent 切换复制 Issue |
| 代码实现与差异 | Git branch / commit / PR | 保留 SHA 和关联 Issue；其他 Agent 在原分支/PR 继续，禁止未经核实重写历史 |
| 自动化验证 | GitHub Actions Checks / Workflow Run + PR 测试说明 | 测试结果需指向具体 SHA；失败不能只报告“稍后修” |
| 真机/人工验证 | Issue 或 PR 中的验收评论（必要时引用经脱敏的构建/日志） | 记录机型、iOS 版本、包 SHA、重现步骤、PASS/FAIL/UNVERIFIED |
| 版本与发布 | Release / tag / CHANGELOG | 与合入 commit、构建、回滚方案对应 |
| `.muse-graph/`、邮件、聊天与模型内部记忆 | **可选索引或交流通道，不是任务事实的唯一来源** | 若保留图谱，尽可能引用 GitHub Issue/PR/SHA，不用多份手工同步材料替代 GitHub |

**不扩张文档数量**：已有 Issue 和 PR 足以留痕时，不强制为每个任务生成交接文档、基线文档、邮件和新的图谱文件。只将长期复用、跨任务适用的约束固化到仓库文档；不得向公开 Issue/PR/Actions 上传 Cookie、token、代理凭据、真实测试账号或敏感日志。

### 8.3 默认执行流程（无需任命角色）

1. **同步事实**：读仓库设计基线、当前 `main`、打开的 Issue/PR、最近 CI/Release；核对可用权限，选择**最早可执行且没有阻塞的任务**。若有未完成的活跃 PR，优先在该 PR 上续做，不跳去开新任务。
2. **接管当前任务**：读同一 Issue 的目标、验收清单、最新状态及关联 PR，检查本地/远端工作树与 SHA；不足的信息在 Issue 留待确认，不从旧聊天猜测。
3. **在原上下文完成**：已有分支/PR 就沿用；没有才新建分支。当前执行 Agent 自行完成方案、实现、测试、修复和 PR 更新。只在必要时请求补充审查，不因历史分工阻碍实施。
4. **证据与验收**：通过实际测试和 CI 产物逐条更新 checklist，关联本次提交 SHA；真机测试与用户审批单独记录，不能把本地 PASS 推断成已发布。
5. **合并与收尾**：按仓库权限、分支保护和用户既有审批规则执行；合并后核对 `main`、CI、Issue 状态以及 Release（如适用），写明下一可执行任务。
6. **继续推进**：默认还是同一个 Agent 接下一个任务；无须重新指派“负责人”。一次只推进一项主开发任务，避免并行覆盖。

**例外**：技术权限不足、目标/安全边界不明或需要用户作出产品决策时，停下受影响操作并在 Issue 写明阻塞与可安全继续的部分；不伪造审批、不暗改需求。

### 8.4 更换 Agent 时的无损接续协议

- **触发条件**：用户主动切换、当前 Agent 不可用、权限不足或经明确判断无法胜任。不要因为“原任务归另一个 Agent”而无意义地转交。
- **离开前**：将已完成工作提交到同一 GitHub 分支（如适合，允许明确标注 WIP 的非主线提交），并在同一个 Issue/PR 最后一条进度评论写：已做到哪里、当前 HEAD SHA、测试/CI 结果、未完成项、阻断、下一步。**禁止提交密钥或把未验证的 WIP 合入 main**。
- **接续时**：新 Agent 先读取 GitHub 上的 Issue、关联 PR、提交、Checks 和设计文档，再核对实际代码；在原任务下面回复“已接续+当前核对结论”，随后继续实现。**无需征得上一 Agent 同意，也不创建重复任务。**
- **未推送代码的边界**：GitHub 无法保存原 Agent 本地未提交、未推送的工作；如无法推送，必须在 Issue 明确“哪些修改不可恢复”，新 Agent 从最后一个可见 SHA 重新验证/补做，不能宣称无损交接。
- **冲突与异常**：保留已发布提交，不随意 `push --force`；发现 HEAD/CI/描述不一致时，先停合并、记录事实、修复后重新验收；若新 Agent 与旧评论结论不同，以可复现代码与证据为准。

最小接续评论（只在切换或较长阻塞时使用，不必每次提交都写）：

```text
[项目接续记录]
Issue / PR：#... / #...
基线：main SHA ...；工作分支 ...；HEAD SHA ...
当前状态：IN_PROGRESS / BLOCKED / CI_PASSED / DEVICE_VERIFIED / ...
已完成：...（对应 commit/check/run 链接）
尚未完成：...（勾选未通过的验收项）
实测结果：命令 + 结果；真机设备/iOS/安装包 SHA（未测明确写未测）
阻断与风险：...；是否需要用户决策：...
下一动作：一项具体、可执行的步骤
```

### 8.5 GitHub Issue 模板（以任务而非 Agent 为中心）

```text
标题：[阶段/切片] 功能名 — 可检验结果
标识：Phase/切片 ID；关联设计/ADR；前置 Issue/PR；可选原图谱 intent
目标：一句话描述最终可观察能力
本次范围 / 明确不做：接口、UI、数据变更、已否决方案
验收清单：逐项 Given / When / Then；PASS 需要的证据级别 E0–E4
技术前提：已验证/未验证 + 证据链接
失败路径：超时、断网、重启、权限拒绝、幂等、迁移与回退
实现入口：相关目录/文件（可后补，避免凭空指定）
关联 PR：#...（建立后补）
进度：NOT_STARTED / IN_PROGRESS / CODE_READY / CI_PASSED / DEVICE_VERIFIED / MERGED / BLOCKED
验证记录：测试命令 + 真实结果 + Actions Run + 构建 SHA + 真机情况
阻断/待用户决策：...；下一动作：...
```

**不写“某 Agent 负责实现/某 Agent 只能审核”。**GitHub Assignee 可以反映当前操作账户，但不具有任务所有权或能力边界；没有 assignee 时也不影响任何有权限的开发 Agent 接续。现存 Issue #12–#14、PR #15、图谱 intent ID 原样保留，不因为流程变更而重复开单或重命名。

### 8.6 PR 自检与合入清单

- [ ] 关联唯一主 Issue 和设计条款；仅改授权范围，列清数据迁移与回滚。
- [ ] 说明实施方案、风险、受影响文件和对应 commit SHA；实际测试命令、结果、CI Run 有链接。
- [ ] 关键实现有正常与失败路径测试；无凭据/账号隐私进入代码、日志、截图或构建产物。
- [ ] **当前执行 Agent 完成代码自检**（安全边界、线程/生命周期、平台回退、旧功能回归）；需要额外专家复核时另加 Reviewer，但不阻止当前 Agent 继续修复。
- [ ] T2/T3 的真机证据与待合并 HEAD 对齐；没有因 Agent 变更而擅自信任历史测试。
- [ ] 无未解决的 P0 或阻断门禁；需用户批准的合并/风险决策已在 GitHub 留痕。
- [ ] 合并后检查 main CI、Issue/Release 状态；按需要更新可选图谱索引，不把图谱更新当作无关任务的必需人工交接环节。

### 8.7 变更控制与事实优先级

1. **Bug 修复**：不改变产品语义时，可在当前任务内直接修复并补回归，不必换 Agent 或多轮审批。
2. **技术路线变化**：需要跨任务复用时，写简短 ADR（问题、选项、证据、影响与退路）链接到 Issue；无需由固定“技术负责人 Agent”审批，但若改变用户已确定功能，必须由用户确认。
3. **范围变化**：涉及删减功能、降级、替换服务或改变隐私/自动行为，当前执行 Agent 暂停对应切片并请求用户决定，不把“技术阻塞”当作自行改需求的授权。
4. **证据冲突**：用户最新明确决策、版本化需求/ADR、Issue 任务范围、可复现提交与 CI/真机证据共同核对；聊天、邮件、图谱摘要只能辅助理解，不能覆盖真实仓库状态。GitHub 记录过期时应修正，不盲从。
